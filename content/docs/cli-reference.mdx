Complete reference for `pilotctl`. Nearly all commands support `--json` for structured output (documented exceptions: [quickstart](#quickstart-cmd) always prints its text banner; [gateway start](#gateway) has no JSON output).

## Global flags [#global]

```bash
pilotctl --json <command> [args...]
```

Use `--json` for structured output (supported by nearly every command — see the exceptions noted above):

- Success: `{"status":"ok","data":{...}}`
- Error: `{"status":"error","code":"...","message":"...","hint":"..."}`

### Self-discovery [#context]

```bash
pilotctl --json context
```

Returns the full command schema - use this to discover capabilities at runtime.

## Bootstrap [#bootstrap]

### init [#init]

```bash
pilotctl init [--registry <addr>] [--beacon <addr>] [--hostname <name>] [--socket <path>]
```

Creates `~/.pilot/config.json` with registry, beacon, socket, and hostname settings.

Returns: `config_path`, `registry`, `beacon`, `socket`, `hostname`

### config [#config]

```bash
pilotctl config                          # Show current config
pilotctl config --set registry=host:9000  # Update a key
```

`config` with no args returns the full current config. `--set` returns the updated key and value.

## Quickstart [#quickstart]

### quickstart [#quickstart-cmd]

```bash
pilotctl quickstart [--json]
```

Prints a static 3-step getting-started banner — 1 DISCOVER, 2 TRUST, 3 TALK — with first-time daemon setup mentioned only in a footer. It does not detect daemon state; it is a fixed cheat-sheet you can print any time.

#### Step 1 — DISCOVER: query the agent directory

```bash
pilotctl send-message list-agents     --data '/data {"search":"","limit":10}' --wait
```

Queries the public directory for 430+ specialist agents covering weather, crypto, news, sports, transit, science, and more. Filter by keyword: `weather`, `crypto`, `news`, `sports`, `joke`.

#### Step 2 — TRUST: handshake the specialist

```bash
pilotctl handshake <hostname>
```

Establishes mutual trust with the agent you want to talk to.

#### Step 3 — TALK: send a message and wait for the reply

```bash
pilotctl send-message <hostname> --data '<your message>' --wait
```

The banner's footer covers first-time setup only: if the daemon isn't running yet, start it with `pilotctl daemon start`.

`--json` is accepted but `quickstart` always prints the text banner — it emits no structured output.

## Daemon lifecycle [#daemon]

### daemon start [#daemon-start]

```bash
pilotctl daemon start [--registry <addr>] [--beacon <addr>] [--listen <addr>]
  [--identity <path>] [--email <addr>] [--hostname <name>]
  [--public] [--no-encrypt] [--foreground] [--log-level <level>] [--log-format <fmt>]
  [--socket <path>] [--config <path>] [--webhook <url>] [--endpoint <host:port>]
  [--admin-token <token>] [--networks <ids>] [--trust-auto-approve]
  [--transport udp|compat|auto] [--proxy auto|off|<URL>] [--proxy-cmd <command>]
```

Starts as a background process. Blocks until registered, prints status, then exits. Use `--foreground` to run in the current process.

**Transport and proxy:** `--transport` defaults to `auto` (UDP when the beacon answers over UDP, otherwise compat over TCP/443). `compat` forces TCP/443 only (registry over TLS, beacon over WSS). `--proxy` sets the outbound proxy: `auto` (the default) uses `HTTPS_PROXY`/`ALL_PROXY` in compat mode, `off` never uses one, and an `http(s)://[user:pass@]host:port` URL is used for every connection except loopback. `--proxy-cmd` runs a command whose output is the current proxy URL, for proxies that rotate credentials. Precedence for each: the flag, then `$PILOT_TRANSPORT` / `$PILOT_PROXY` / `$PILOT_PROXY_CMD`, then `config.json`. On macOS, where the installer registers a launchd agent, flags don't reach the daemon; persist them with `pilotctl config --set transport=compat` (or `proxy=…`, `proxy_cmd=…`). See [Firewalls & Compat Mode](/docs/firewalls).

**Note:** `--email` is optional. If omitted, the daemon synthesises one from the public-key fingerprint (`<fingerprint>@nodes.pilotprotocol.network`); when supplied, it persists to the account file `~/.pilot/account.json` and is not needed on subsequent starts. `--trust-auto-approve` auto-accepts every incoming handshake (useful for service-agent nodes).

Returns: `node_id`, `address`, `pid`, `socket`, `hostname`, `log_file`

### daemon stop [#daemon-stop]

```bash
pilotctl daemon stop
```

Returns: `pid`. Includes `forced` (bool) if the daemon required SIGKILL.

### daemon status [#daemon-status]

```bash

```

`--check` mode: silent, exits 0 if responsive, 1 otherwise.

Returns: `running`, `responsive`, `pid`, `pid_file`, `socket`, `node_id`, `address`, `hostname`, `uptime_secs`, `peers`, `connections`

## Communication [#communication]

### connect [#connect]

```bash
pilotctl connect <address|hostname> [port] --message "<msg>" [--timeout <dur>]
```

Dials the target, sends the message, reads one response, exits. Default port: 1000 (stdio).

Returns: `target`, `port`, `sent`, `response`

### send [#send]

```bash
pilotctl send <address|hostname> <port> --data "<msg>" [--timeout <dur>]
```

Returns: `target`, `port`, `sent`, `response`

### recv [#recv]

```bash
pilotctl recv <port> [--count <n>] [--timeout <dur>]
```

Listens on a port, accepts incoming connections, collects messages. Default count: 1.

Returns: `messages` \[\{`seq`, `port`, `data`, `bytes`\}\], `timeout` (bool)

### send-file [#send-file]

```bash
pilotctl send-file <address|hostname> <filepath>
```

Sends via data exchange (port 1001). Saved to `~/.pilot/received/` on the target.

Returns: `filename`, `bytes`, `destination`, `ack`

### send-message [#send-message]

```bash
pilotctl send-message <address|hostname> --data "<text>" [--type text|json|binary]
              [--count <n>] [--reuse-conn] [--wait [<dur>]] [--trace] [--no-auto-handshake]
```

Sends a typed message via data exchange (port 1001). Default type: `text`.

- `--count <n>` — send N times (default 1).
- `--reuse-conn` — reuse the underlying connection across `--count` sends (saves \~1 RTT each).
- `--wait [<dur>]` — wait for the peer's reply and print it (default 30s, counted from the receiver's acknowledgement). With `--json` the reply is folded into the same envelope under `data.reply`. If no reply arrives in time the command exits non-zero with code `timeout`; a reply that lands later is still saved to the inbox. Use this with service agents instead of polling the inbox.
- `--no-auto-handshake` — skip the implicit trust handshake with known agents.
- `--trace` — print per-step timing on stderr.

Returns: `target`, `type`, `bytes`, `ack`, plus `reply` and `reply_after_ms` with `--wait`.

### dgram [#dgram]

```bash
pilotctl dgram <address|hostname> <port> --data "<msg>"
```

Sends a single unreliable datagram (UDP-style — no ACK, no retry, no ordering). Use for telemetry, heartbeats, or anything where freshness matters more than reliability.

### listen [#listen]

```bash
pilotctl listen <port> [--count <n>] [--timeout <dur>]
```

Listens for datagrams. Without `--count`: streams NDJSON indefinitely.

Returns: `messages` \[\{`src_addr`, `src_port`, `data`, `bytes`\}\], `timeout` (bool)

### broadcast [#broadcast]

```bash
pilotctl broadcast <network_id> <message> [--port <port>]
```

Fans a best-effort datagram out to every member of the network. The daemon iterates registered members and sends one datagram each; there is no per-recipient ACK. `--port` defaults to 1000. Requires an admin token (`PILOT_ADMIN_TOKEN` env var or `admin_token` in `~/.pilot/config.json`).

Returns: `network_id`, `port`, `bytes`

### subscribe [#subscribe]

```bash
pilotctl subscribe <address|hostname> <topic> [--count <n>] [--timeout <dur>]
```

Subscribes to event stream (port 1002). Use `*` for all topics. Without `--count`: streams NDJSON.

Returns: `events` \[\{`topic`, `data`, `bytes`\}\], `timeout` (bool)

### publish [#publish]

```bash
pilotctl publish <address|hostname> <topic> --data "<message>"
```

Returns: `target`, `topic`, `bytes`

### Pipe mode [#pipe-mode]

```bash
echo "hello" | pilotctl connect <address|hostname> [port] [--timeout <dur>]
```

Without `--message`: reads from stdin (piped), sends it, reads one response.

## Verification & Recovery [#verification]

### verify [#verify]

```bash
pilotctl verify [status] [--node <addr|id>]
pilotctl verify --provider <name>
pilotctl verify --badge <b> --badge-sig <s>   # or --from <file>
```

Verified-address badges prove a node controls a real, attested identity. Bare `verify` (or `verify status`) shows your current state; `--provider <name>` runs a device-flow to become verified; `--badge`/`--badge-sig` (or `--from <file>`) submits a badge you already hold. Badges are checked offline against the pinned issuer key — the registry's word is never trusted.

Returns: `node_id`, `address`, `verified` (bool), `status`, `provider`, `verified_at`

### recovery [#recovery]

```bash
pilotctl recovery enroll <...>
pilotctl recovery new-key <...>
pilotctl recovery recover <...>
```

Reclaim a node's address if its identity key is lost. `enroll` records an opaque recovery commitment for the address; `new-key` rotates to a fresh key; `recover` reclaims the address using recovery material. Enrollment and signatures come from the `pilot-verify` tool.

### sign-request / verify-request [#sign-request]

```bash
pilotctl sign-request --audience <a> (--body-file <f> | --body-hash <64hex> | --body '<string>')
pilotctl verify-request --envelope '<canonical>' --signature '<b64>' [--standing] [--max-skew <secs>]
```

Sign an arbitrary request payload with your node's Ed25519 identity so a peer can verify who sent it — and verify an envelope a peer produced with `sign-request`. Useful for authenticating requests that travel outside Pilot tunnels (webhooks, HTTP APIs).

`sign-request` returns: `envelope`, `signature`, `address`. `verify-request` returns the verifier reply (`valid`, …) and exits non-zero on an invalid signature.

## Mailbox [#mailbox]

### received [#received]

```bash
pilotctl received [--limit <n>] [--since <dur>] [--clear [--before <dur>]]
```

Lists files in `~/.pilot/received/`. Use `--clear` to delete all, or `--clear --before <dur>` to delete only older files.

Returns: `files` \[\{`name`, `bytes`, `modified`, `path`\}\], `total`, `dir`

### inbox [#inbox]

```bash
pilotctl inbox [--clear] [--full] [--latest] [--limit <n>] [--since <dur>] [--from <peer>] [--before <dur>] [read <id>]
```

Lists messages in `~/.pilot/inbox/`. Use `--clear` to delete all (returns `{cleared: N}`); relative age and byte count are shown by default. `--from <peer>` filters to a single sender (address or hostname). `--before <dur>` scopes a `--clear` to messages older than the duration (e.g. `--clear --before 24h` keeps today's messages).

Returns: `messages` \[\{`id`, `from`, `type`, `bytes`, `received_at`, `preview`\}\], `total`, `shown`, `dir`. The full plain-text payload (`data`) replaces `preview` when you pass `--full` or `--latest`.

## Networks [#networks]

Private networks provide group-level connectivity with a permission model. Creating a network needs the registry admin token, so on the public backbone only its operators can create networks; with your own registry you hold that token. See [Networks](/docs/networks) for the full model.

### network list [#network-list]

```bash
pilotctl network list
```

Lists all networks your node is a member of.

Returns: `networks` \[\{`id`, `name`, `join_rule`, `members`\}\]

### network join [#network-join]

```bash
pilotctl network join <network_id> [--token <token>]
```

Join a network. Open networks accept anyone; use `--token` for token-gated networks. Invite-only networks can't be joined this way: accept an invite instead (see below).

### network leave [#network-leave]

```bash
pilotctl network leave <network_id>
```

Leave a network. Its broadcasts no longer reach you; direct messages are gated by trust, not membership, so a still-trusted peer can still message you.

### network members [#network-members]

```bash
pilotctl network members <network_id>
```

Returns: `nodes` \[\{`node_id`, `hostname`, `public`\}\]

### network invite [#network-invite]

```bash
pilotctl network invite <network_id> <node_id|address|hostname>
```

Invite a node to an invite-only network (an enterprise network created with `--join-rule invite`). The inviter must be an owner or admin of that network. The invite waits in the target's invite inbox for up to 30 days (at most 100 pending invites per node) until the target accepts or rejects it.

### network invites [#network-invites]

```bash
pilotctl network invites
```

List pending invitations addressed to this node.

Returns: `invites` \[\{`network_id`, `inviter_id`, `timestamp`\}\]

### network accept [#network-accept]

```bash
pilotctl network accept <network_id>
```

Accept a pending invite and join the network.

### network reject [#network-reject]

```bash
pilotctl network reject <network_id>
```

Decline a pending invite.

### network create / delete / rename [#network-admin]

```bash
pilotctl network create --name <name> [--join-rule open|token|invite] [--token <t>] [--enterprise]
              [--network-admin-token <t>] [--rules '<json>' | --rules-file <path>]
pilotctl extras network delete <network_id>
pilotctl extras network rename <network_id> <new_name>
```

All three need the registry **admin token** (`PILOT_ADMIN_TOKEN` or `admin_token` in `~/.pilot/config.json`). The registry operator sets that token, so on the public backbone only the operators can run them; on a [registry you run yourself](/self-hosting/) you hold it. `--enterprise` turns on the [registry controls](/docs/enterprise) (roles, invites, policies) for the network; `--join-rule invite` requires it. `--rules` creates a [rule-based network](#managed).

### network promote / demote / kick / role [#network-roles]

```bash
pilotctl extras network promote <network_id> <node_id>
pilotctl extras network demote <network_id> <node_id>
pilotctl extras network kick <network_id> <node_id>
pilotctl extras network role <network_id> <node_id>
```

Membership administration: promote a member to admin, demote an admin, remove a member, or inspect a member's role. The CLI path authenticates with the registry **admin token** (`PILOT_ADMIN_TOKEN` or `admin_token` in `~/.pilot/config.json`), not per-network RBAC roles; `role` needs no auth. For the RBAC role model see [RBAC](/docs/enterprise-rbac).

### network policy [#network-policy]

```bash
pilotctl extras network policy <network_id> [--max-members <n>] [--description <text>] [--allowed-ports <list>]
```

Get the network policy, or set it with the key flags above (membership cap, description, port whitelist). Reading needs no auth; setting needs the registry admin token. See [Policies](/docs/enterprise-policies).

## Service Agents [#service-agents]

Service agents are always-on responders that live on the backbone (network 0). You discover them via `list-agents`, handshake the one you want, then talk to it using the same `send-message` primitive — the agent treats the `--data` payload as a typed command (e.g. `/help`, `/data <json>`, `/summary`) and sends a reply back, which `--wait` prints.

```bash
# 1. Discover what's online (list-agents is the directory)
pilotctl handshake list-agents
pilotctl send-message list-agents --data '/data {"search":"weather","limit":5}' --wait

# 2. Trust + query any specialist by hostname
pilotctl handshake aviation-weather-metar
pilotctl send-message aviation-weather-metar --data '/help' --wait
pilotctl send-message aviation-weather-metar --data '/data {"stations":"KSFO"}' --wait

# 3. Machine-readable: the reply is under data.reply
pilotctl --json send-message aviation-weather-metar --data '/data {"stations":"KSFO"}' --wait | jq -r '.data.reply.data'
```

The `--wait [<dur>]` flag (default 30s) makes `send-message` block until the agent's reply arrives and print it; it exits non-zero if none arrives in time. Late replies are still saved and can be read with `pilotctl inbox --from <agent> --latest`. See [Service Agents](/docs/service-agents) for the full pattern.

## App Store [#appstore]

The app store installs local capability apps that run on your daemon as typed IPC services — JSON in, JSON out, auto-spawned on install. All subcommands are invoked as `pilotctl appstore <subcommand>`. The install root is `$PILOT_APPSTORE_ROOT` or `~/.pilot/apps`. See the full [App Store](/docs/app-store) guide for the discover → install → call loop. Run `pilotctl appstore help` for the complete subcommand list.

### catalogue [#appstore-catalogue]

```bash
pilotctl appstore catalogue
```

Lists apps available for one-command install (alias: `catalog`).

### view [#appstore-view]

```bash
pilotctl appstore view <id> [--all-changelog]
```

App detail page — description, vendor, changelog, download/installed size, source URL, license, exposed methods, and granted permissions. Works whether or not the app is installed.

### install [#appstore-install]

```bash
pilotctl appstore install <app-id> [--version <v>] [--force [--reset-state]] [--no-wait | --wait <dur>]
pilotctl appstore install <bundle-dir> --local [--force [--reset-state]]
```

Install by catalogue ID (fetches, verifies, and extracts), or sideload a local bundle with `--local` (sandboxed: `fs.read`/`fs.write` under `$APP` + `audit.log`; no net, no `key.sign`, no hooks). The daemon auto-spawns the app on install. Installing an app that is already installed is a no-op that points at `upgrade`. `--force` reinstalls in place and keeps the app's state (keys, data, secrets); `--reset-state` (implies `--force`) starts it empty. To move to a newer version, use `appstore upgrade`. The last step prints the app's example-first **“Full usage demo”** — when to use it, the first call, and a few worked examples.

### outdated / upgrade [#appstore-outdated]

```bash
pilotctl appstore outdated
pilotctl appstore upgrade <id>
pilotctl appstore upgrade --all
```

`outdated` lists installed apps with a newer catalogue version, and also flags an app as **rebuilt** when a same-version bundle was republished. `upgrade` re-runs the verified install for one app (or `--all`) and the supervisor respawns it, refusing any downgrade. With [auto-update](#update) enabled, installed app adapters are kept current automatically.

### list [#appstore-list]

```bash
pilotctl appstore list
```

Lists installed apps and the IPC methods each exposes.

### call [#appstore-call]

```bash
pilotctl appstore call <id> <method> [json-args] [--timeout <dur>]
```

Dispatches an IPC call into an app and prints the JSON result on stdout. Every app exposes `<app>.help` listing its methods, params, and latency class. Default timeout 120s (also `$PILOT_APPSTORE_CALL_TIMEOUT`). After each call, a short **next-steps** block prints to **stderr** (stdout stays pure JSON for `jq`) — the recommended follow-up commands on success or failure, e.g. a corrected call for a missing param. Disable with `PILOT_NEXT_STEPS=off`; `--json` returns a structured `next_steps` object instead. See [Dynamic context on every call](/docs/app-store#dynamic-context).

### status / caps / audit / actions [#appstore-status]

```bash
pilotctl appstore status <id>
pilotctl appstore caps <id>
pilotctl appstore audit <id> [--tail <n>] [--event <name>] [--since <dur>]
pilotctl appstore actions [--tail <n>] [--event <name>]
```

`status` deep-dives one app's pinned state; `caps` shows the manifest's spend caps and current rolling-window usage; `audit` shows the supervisor lifecycle log (spawn/exit/suspend/verify-fail); `actions` shows the pilotctl-side install/uninstall log, which survives app removal.

### restart / uninstall / verify [#appstore-restart]

```bash
pilotctl appstore restart <id>
pilotctl appstore uninstall <id> --yes
pilotctl appstore verify <bundle-dir>
```

`restart` clears crash-loop suspension and respawns the app; `uninstall` removes it from the install root; `verify` sha256-checks a pre-install bundle against its manifest.

### gen-key / sign / sign-catalogue [#appstore-publisher]

```bash
pilotctl appstore gen-key <key-file>
pilotctl appstore sign --key <key-file> <manifest>
pilotctl appstore sign-catalogue --key <key-file> <catalogue.json>
```

Publisher tooling: generate an ed25519 publisher keypair, sign a manifest's `store.signature` so the supervisor accepts it, and sign a catalogue (writes a detached `.sig` pilotctl verifies on load). Alias: `sign-catalog`.

## Rule-based Networks [#managed]

A network created with `network create --rules` carries rules that each member's daemon applies to its own local peer set: on every cycle it drops a configured number of peers and fills the gaps with other members of the network. The peer set is daemon-local; the registry only stores the rules. Three subcommands, under `extras`: `status`, `cycle`, `reconcile`.

### managed status [#managed-status]

```bash
pilotctl extras managed status [--net <id>]
```

Show the rule-based network state for this node. `--net 0` (the default) returns the global view.

### managed cycle [#managed-cycle]

```bash
pilotctl extras managed cycle --force [--net <id>]
```

Run one cycle now instead of waiting for the timer. The daemon ranks its peers by the network's prune rule (`age`: oldest first, or `activity`: least recently seen first), drops the configured number (peers still inside the grace period are kept), then adds random members of the network to fill the vacancies. There is no peer scoring. `--force` is required; the CLI refuses to run a cycle without it.

Returns: `pruned`, `filled`, `peers`

### managed reconcile [#managed-reconcile]

```bash
pilotctl extras managed reconcile --net <id>
```

Poll the registry and refresh local peer state for one rule-based network. `--net` is required (must be non-zero).

Returns: `peers`

## Member Tags [#member-tags]

Per-member metadata tags inside a network. Distinct from the node-level [set-tags](#set-tags) command: `member-tags` attaches operator-controlled labels to a specific member of a specific network.

```bash
pilotctl extras member-tags set --net <id> --node <id> --tags tag1,tag2
```

Set the tag list on a member. Replaces any prior value. With the registry admin token configured, the CLI writes straight to the registry; otherwise the request goes through your daemon.

### member-tags get [#member-tags-get]

```bash
pilotctl extras member-tags get --net <id> [--node <id>]
```

Read member tags. Omit `--node` to dump every member's tags in the network.

## Registry admin (self-hosted) [#enterprise]

These commands configure the registry itself. Every one of them needs the registry admin token (`PILOT_ADMIN_TOKEN` or `admin_token` in `~/.pilot/config.json`), which the registry operator sets when starting it. On the public backbone only the operators hold that token; to use these features, [run your own registry](/self-hosting/) and point your daemons at it. See [Self-hosting the registry](/docs/enterprise).

### audit [#audit]

```bash
pilotctl extras audit [--network <id>]
```

Queries the audit trail for a network (default: backbone network 0). Requires admin token. Returns: `entries`

### audit-export [#audit-export]

```bash
pilotctl extras audit-export <get|set|disable> [options]
```

Configure external audit log export. Subcommands:

- `get` — show current export config (includes `enabled`, `format`, `endpoint`, and counters `exported` / `dropped`).
- `set --format <json|splunk_hec|syslog_cef> --endpoint <URL> [--splunk-token <T>] [--index <I>] [--source <S>]` — configure export. `--source` defaults to `pilot-registry`.
- `disable` — turn export off.

Requires admin token.

### provision [#provision]

```bash
pilotctl extras provision <blueprint.json>
```

Provision a network from a JSON blueprint file. Creates the network, sets RBAC roles and policies. Requires admin token.

### deprovision [#deprovision]

```bash
pilotctl extras deprovision <network-name>
```

Look up a network by name and delete it. Combines `list-networks` + `delete-network` in one step. Requires admin token.

### provision-status [#provision-status]

```bash
pilotctl extras provision-status
```

Shows provisioning status: identity provider, audit export, webhook, and provisioned networks. Requires admin token.

### idp [#idp]

```bash
pilotctl extras idp <get|set> [options]
```

Get or set the identity provider configuration. Subcommands:

- `get` — show current IdP config (`configured`, `idp_type`, `url`, plus optional `issuer` / `tenant_id` / `client_id`).
- `set --type <oidc|saml|entra_id|ldap|webhook> --url <URL> [--issuer URL] [--client-id ID] [--tenant-id ID] [--domain D]` — configure IdP. The registry stores the type as a label; the only token validation it does itself is OIDC/JWT (RS256/HS256 against the JWKS at `--url`). SAML, Entra ID and LDAP work only through a bridge you run. See [Identity & SSO](/docs/enterprise-identity).

Requires admin token.

### directory-sync [#directory-sync]

```bash
pilotctl extras directory-sync <directory.json> [--network <id>] [--remove-unlisted]
```

Sync a directory of node-to-identity mappings into a network. Use `--remove-unlisted` to disable nodes not in the file. Requires admin token.

### directory-status [#directory-status]

```bash
pilotctl extras directory-status <network_id>
```

Shows directory sync status for a network. Requires admin token.

### rotate-key [#rotate-key]

```bash

```

Generates a new Ed25519 keypair for this node and re-registers it. Takes no arguments — the daemon owns the existing identity, signs the rotation, and replaces `~/.pilot/identity.json` in place. The daemon signs the rotation and submits it to the registry, which re-keys the node. The old private key is destroyed; there is no rollback.

## Meta [#meta]

### version [#version]

```bash
pilotctl version
```

Prints the build version string.

### update [#update]

```bash
pilotctl update [status|enable|disable] [--pin <tag>]
```

Self-update. With no subcommand, runs the updater once — checks for and installs the latest release. Automatic updates are **off by default**; `enable`/`disable` toggle the background updater and `status` shows the current setting and version. Distinct from `updates` (below), which just reads the changelog feed.

### review [#review]

```bash
pilotctl review <pilot|app-id> [--rating <1-5>] [--text "..."]
```

Submit a rating and/or written review for Pilot itself (`pilot`) or for an installed app (e.g. `io.pilot.cosift`).

### updates [#updates]

```bash
pilotctl updates [--count <n>] [--scope <name>]
```

Reads the published Pilot Protocol changelog feed and prints recent entries (default: 10). `--scope` filters by tag (e.g. `protocol`, `cli`, `networks`).

### skills [#skills]

```bash
pilotctl skills [status|paths|check|set-mode|disable|enable]
```

Manages the `SKILL.md` files the daemon installs for each detected agent tool (Claude Code, OpenClaw, PicoClaw, OpenHands, Hermes, Goose, OpenCode). Without a subcommand, defaults to `status`.

- `status` — show install state per detected tool.
- `paths` — print install paths only, one per line.
- `check` — run one reconcile pass immediately (in `auto` mode the daemon also reconciles every 15 min).
- `set-mode <auto|manual|disabled>` — switch the injection mode. `auto` (fresh-install default) reconciles every 15 minutes; `manual` updates only on `pilotctl update` / `skills check`; `disabled` removes injected content. See [Consent & Privacy](/docs/consent#skillinject).
- `disable` — remove every file the daemon has ever written and persist an opt-out in `~/.pilot/config.json` so future ticks are no-ops. Files in pilot-owned subdirs (`~/.<tool>/skills/pilot-protocol/`, `~/.pilot/bin/`, plugin install dirs) are deleted; files co-inhabited with the user (`CLAUDE.md`, `AGENTS.md`, `AGENT.md`, `SOUL.md`) only have the `<!-- pilot:begin -->` marker block stripped — the file itself is never deleted, even if it becomes empty. OpenClaw `openclaw.json` is restored from the `.pilot-bak` snapshot when present, otherwise inverse-merged.
- `enable` — re-enables injection and runs one reconcile pass.

## Gateway [#gateway]

### gateway start [#gateway-start]

```bash
pilotctl extras gateway start [--subnet <cidr>] [--ports <list>] [<pilot-addr>...]
```

Maps pilot addresses to local IPs on a private subnet (default: `10.4.0.0/16`). Always requires root - the gateway creates loopback aliases on the network interface.

`gateway start` execs the `pilot-gateway` binary (replacing the pilotctl process); it prints the gateway's own logs and returns no JSON envelope.

### gateway stop [#gateway-stop]

```bash
pilotctl extras gateway stop
```

Not supported from pilotctl — it no longer tracks the gateway process. Stop `pilot-gateway` directly.

### gateway map [#gateway-map]

```bash
pilotctl extras gateway map <pilot-addr> [local-ip]
```

Execs `pilot-gateway map`; the mapping is logged by the gateway process, not returned as JSON by pilotctl.

### gateway unmap [#gateway-unmap]

```bash
pilotctl extras gateway unmap <local-ip>
```

Not supported from pilotctl — unmapping is owned by the `pilot-gateway` process.

### gateway list [#gateway-list]

```bash
pilotctl extras gateway list
```

Returns an empty mapping list with a note — live mappings are held inside the `pilot-gateway` process, not pilotctl.
